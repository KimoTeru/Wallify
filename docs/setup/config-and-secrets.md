# Конфигурация и секреты

Где лежат адрес бэкенда, ключи доступа и как они попадают в приложение. Ключи в git не попадают никогда.

Related: `architecture/data.md` § Сеть, `setup/gradle-conventions.md`.

## Правила

1. Адрес бэкенда публичный и встроен в код: константа `API_BASE_URL` в `apiNetworkConfig`. Через сборку и
   `local.properties` он не настраивается.
2. Ключи бэкенда не пишем в код, `gradle.properties`, README и тесты. Источники — `local.properties` (в `.gitignore`)
   и переменные окружения.
3. В тестах используем вымышленный хост (`https://api.example.com/`) и фейковые ключи.
4. Оба ключа — ключ доступа и секретный ключ — обязательны, значений по умолчанию нет. Без любого из них
   `generateApiConfig` падает с сообщением, какие значения не заданы, поэтому не собирается ни приложение, ни тесты
   модулей, зависящих от `core:network`. Пустую строку вместо ключа не подставляем.
5. Ключ доступа уходит в статический заголовок авторизации (`apiNetworkConfig`). Секретный ключ в запросы не попадает:
   он нужен только там, где пользовательская авторизация обменивается на токен, и приходит туда как `ApiCredentials`
   из `core:network`. Его и ключ доступа не логируем: `ApiCredentials.toString()` значения скрывает.
6. Ключи вшиваются в сборку, поэтому их можно извлечь из готового приложения. Бэкенд требует держать их
   конфиденциальными: для публичного релиза запросы с ключами переносим на собственный прокси, а в приложении
   оставляем только адрес прокси.
7. Новое секретное значение добавляется так же, как существующие: `localSecret(property, env, default)` в
   `build-logic` → `GenerateApiConfigTask` → константа в `ApiBuildConfig` → привязка в `NetworkModule`. Приложения
   значения не передают. Если значение обязательное, проверка — в `GenerateApiConfigTask`.

## Откуда берутся значения

| Что | `local.properties` | Переменная окружения |
|---|---|---|
| Ключ доступа (обязателен) | `api.accessKey` | `API_ACCESS_KEY` |
| Секретный ключ (обязателен) | `api.secretKey` | `API_SECRET_KEY` |
- Значения читает convention-плагин `wallify.api.config` (подключён в `core:network`) при сборке и генерирует
  `ApiBuildConfig` в `core/network/build/generated/apiConfig`. Файл лежит в `build/`, в git он не попадает.
  Одинаково для Android и Desktop.
- Переменные окружения нужны при сборке, а не при запуске: для Desktop задавайте их в Run Configuration Gradle-задачи
  или в `local.properties`.
- После смены значений пересоберите проект: задача `generateApiConfig` обновит константы.
- Правило чтения: сначала `local.properties`, потом окружение.

## Вход пользователя

Вход идёт через системный браузер, поэтому в список Redirect URI приложения на сайте бэкенда нужно добавить оба адреса
возврата (по одному на строку), иначе авторизация завершится ошибкой:

```
wallify://oauth/callback
http://127.0.0.1:49721/oauth/callback
```

Первый принимает Android (ссылка на `MainActivity`), второй — Desktop (временный сервер на петлевом интерфейсе,
порт задан в `JvmAuthBrowser`). Сменили адрес или порт в коде — смените и список там. Своего сервера для входа не
нужно. Запрашиваются все права бэкенда (`AuthApi`).

## Где живёт всё, что специфично для бэкенда

`core:network`: `apiNetworkConfig` (адрес, имена и значения статических заголовков), API-классы и модели запросов и ответов. Остальной код
от конкретного бэкенда не зависит (`architecture/data.md` § Сеть).
