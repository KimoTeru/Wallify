# Данные: Response, сеть, сессия, хранилища, пагинация

Как устроен слой данных. Что куда класть по слоям — `architecture/layers.md`.

Related: `setup/config-and-secrets.md`, `code/di.md`, `design/foundations.md` § Списки.

## Response

`Response<T>` из `core:common` — единственный тип результата операции данных: `Response.Success(data)` или
`Response.Error(ResponseError(message, code))`. Второго типа результата нет.

- `code` — HTTP-статус; `ResponseError.DEBUG_ERROR_CODE` (`-1`), если кода нет (сеть недоступна, ошибка разбора).
- Обработка: `map`, `flatMap`, `onSuccess`, `onError`, `handleResponse`, `getOrNull`; зависимые вызовы подряд —
  `combineResponse` (до пяти шагов), независимые — `combineResponses`.
- Блок, который может бросить исключение, оборачивается в `responseOf { … }`: `CancellationException`
  пробрасывается, остальное становится `Response.Error`.
- Типизированная ошибка (код, enum бэкенда) — `DetailedResponse<T, E>`; `executeRequestWithErrorCode` возвращает
  `DetailedResponse<T, Int>`.
- Состояние загрузки для UI — `Resource<T>` (`Loading` / `Success` / `Error`), строится через `asResource()` и
  `asResourceFlow()`.
- `catch (e: Exception)` в `suspend`-коде всегда пропускает `CancellationException`.

## Сеть

`core:network`. Один `HttpClient` из Koin, собирается `HttpClientFactory`.

- Запрос — `executeRequest<XxxResponse> { client.get("path") }`, возвращает `Response<XxxResponse>`. Не-2xx превращается в
  `Response.Error` с HTTP-кодом; текст берётся из тела (`ApiErrorBody`: `errors`, `message` или `error`).
- API-класс — маленький класс с `HttpClient` в конструкторе и методами по эндпоинтам; относительные пути, без
  базового адреса.
- Базовый адрес, таймауты, логирование и статические заголовки приходят из `NetworkConfig`. Адрес и всё, что
  специфично для бэкенда (имена и формат заголовков авторизации и версии), определено в `apiNetworkConfig`.
  Имена query-параметров, форматы тел запросов, модели `XxxRequest` / `XxxResponse` — в API-классах (`api/`) и
  `model/request`, `model/response` модуля `core:network`. Остальной код этих деталей не знает: репозиторий
  принимает модели и enum'ы из `core:model`, а в строки и значения параметров их превращает API-класс
  (`toQuery()` в `api/RequestParameters.kt`).
- Модель ответа (`XxxResponse`) полная: в ней все поля из документации бэкенда, чтобы смена потребностей приложения
  не требовала правки сети. `@Serializable` с `@SerialName` для snake_case, у каждого свойства аннотация на своей
  строке; необязательные поля `null` по умолчанию, списки — `emptyList()`. Даты остаются строками: библиотеки дат в
  проекте нет. Поле без документированной формы — `JsonElement` / `JsonObject`.
- Доменная модель (`core:model`) — только то, что нужно приложению; без значений по умолчанию, `null` там, где
  данных может не быть, иначе подставляем значение в маппере (`?: String.Empty`, `?: 0`). Новое поле добавляем в
  модель, когда оно понадобилось экрану; в `XxxResponse` оно уже есть.
- Маппер — публичная функция-расширение в том же файле, что и модель: `XxxResponse.toDomain()` под моделью ответа,
  `XxxParams.toRequest()` под моделью запроса. Отдельных файлов мапперов нет; у каждой вложенной модели свой
  `toDomain()`. Вызывает его `XxxRemoteDataSourceImpl` (импорт `…model.response.<область>.toDomain`).
- Запрос с телом — форма (`formContent(...)` из `core:network`), `null`-поля в тело не попадают.
- Ответ с пустым телом (204) — `executeRequest<Unit>`.
- Цепочка для данных бэкенда: `XxxApi` (`core:network`, `Response<XxxResponse>`) → `XxxRemoteDataSource` + `Impl`
  (`core/data/.../remote/`, вызывает API и `toDomain()`) → `XxxRepository` + `Impl` (пагинация, кэш в Room: § Кэш).
  Методы: `getXxx`, `searchXxx`, постраничные — `getXxxFlow`.
- Логирование HTTP включено в debug-сборке и выключено в release (`AppBuild` из `core:network`): на Android — флаг
  `debuggable` приложения, на Desktop — свойство `wallify.debug`, которое задают только задачи `run` и `hotRun`
  (`build-logic`). Заголовок `Authorization` в логах скрыт (`sensitiveHeaders`).
- Динамические заголовки (токен пользователя, язык) добавляет `AuthHeadersPlugin` из `HeadersCollectorRepository`;
  вручную в запросах их не ставим.
- Для скачивания произвольных файлов используется отдельный `DownloadHttpClient` без базового адреса и без
  заголовков API — ключ не уходит на сторонние хосты.
- Состояние сети — `NetworkMonitor`; фичи видят его только как `ConnectivityRepository` из `core:domain`.
- Новый API-класс тестируется через `MockEngine` (`NetworkClientTest`).

## Бэкенд фото

Правила API (Unsplash), которые выполняет код:

- Картинки показываем только по URL из ответа (`PhotoUrls`); размер меняем параметрами этого URL, `ixid` из него не
  убираем. Ключ на хост картинок не отправляем: файлы качает `DownloadHttpClient`.
- Каждое «скачивание» фото (сохранить, поставить обоями) сопровождается `PhotoRepository.trackDownload(photoId)`;
  без этого вызова файл не качаем.
- Показывая фото, указываем автора и источник со ссылками на их профили; в ссылки добавляем
  `utm_source=<имя приложения>&utm_medium=referral`. Это делает слой сети (`withReferral()` в мапперах
  `Photo.htmlUrl` и `User.profileUrl`): экраны открывают эти ссылки как есть.
- Скачивание фото в приложении — через браузер: `trackDownload(photoId)` возвращает адрес файла, экран открывает его
  (`LocalUriHandler`); платформенного сохранения файла нет.
- Камера и параметры съёмки (`Photo.exif`), принадлежность фото коллекциям пользователя
  (`Photo.currentUserCollectionIds`) приходят только в полном фото (`getPhoto`), в списках их нет.
- Лимит страницы — 30 (`DEFAULT_PAGE_SIZE`); в демо-режиме 50 запросов в час, исчерпание приходит как 403.
- Название бэкенда не используем в имени приложения и в иконке.
- Пользовательские запросы (`/me`, коллекции пользователя, изменение фото) работают только с токеном пользователя
  (`Bearer`, см. § Сессия); с одним ключом доступа бэкенд отвечает 401.

## Сессия

- `SessionRepository` хранит токен пользователя в DataStore (`updateAuthToken`, `clear`). Нет токена — приложение
  работает как анонимный клиент со статическим ключом.
- `SessionHeadersSynchronizer` стартует вместе с Koin и сводит токен и язык (из `UserSettings` или системный) в
  `HeadersCollectorRepository`. Токен уходит как `Bearer <token>`, заменяя статический заголовок авторизации.
- Истёкшая сессия: любой код, увидевший 401 (`ResponseError.isUnauthorized`), вызывает
  `ApiErrorManager.emitEvent(SessionExpired)`; корневой экран очищает сессию (`code/presentation.md` § Общие блоки),
  и граф показывает экран входа. Образец — `UserSessionSynchronizer`: он в слое данных и не знает про
  `ApiErrorManager`, поэтому очищает сессию сам.
- Данные, нужные многим экранам (вошедший пользователь), экраны не загружают. Их грузит слой сессии и держит
  репозиторий в `StateFlow`: `UserSessionSynchronizer` следит за `Authorization` из `HeadersCollectorRepository` (а не
  за сохранённым токеном: запрос должен уйти уже с новым токеном), при новом токене вызывает
  `UserRepository.refreshCurrentUser()`, без токена — `clearCurrentUser()`. Экран читает `UserRepository.currentUser`.
  Синхронизаторы стартуют вместе с Koin (`@Singleton(createdAtStart = true)` в `DataModule`).
- Слой данных не показывает диалоги, но и не прячет сбои: фоновая работа открывает их в домене интерфейсом
  (`UserSessionManager.loadError`), а корень (`RootGraphLogic`) решает, что показать. Так сбой загрузки пользователя
  (не 401) даёт общий диалог, но только пока устройство в сети: без сети виден баннер, а загрузка повторяется сама
  при каждом возврате сети. Фоновой повтор ждёт возврата сети, а не крутится по таймеру.
- Вход пользователя — `AuthRepository.signIn()` (OAuth, код авторизации, системный браузер): одним вызовом
  открывает страницу входа, ждёт возврата пользователя, меняет код на токен и кладёт его в `SessionRepository`;
  экран токен не видит. Результат — `Response<Boolean>`: `true` вошёл, `false` отказался или не вернулся за 5 минут,
  `Error` — браузер не открылся или бэкенд отклонил код. Ожидание отменяется отменой корутины. Выход — `signOut()`;
  токен бессрочный, отзывать его на бэкенде нечем. Какой экран показать по сессии, решает корневой граф
  (`code/navigation.md` § Экран по сессии).
- Браузер открывает платформенный `AuthBrowser` (`core:platform`) и сам знает свой `redirectUri`: Android — ссылка
  `wallify://oauth/callback`, которую принимает `MainActivity` (`singleTask`) и отдаёт в `AuthRedirectBus`;
  Desktop — временный HTTP-сервер на `127.0.0.1` (`JvmAuthBrowser`), живущий только пока идёт ожидание.
- Адреса авторизации, список прав и имена полей — в `AuthApi` (`core:network`); `redirect_uri` приходит ей аргументом.
  Секретный ключ уходит только в запрос токена.

## Хранилища

| Что | Где | Правило |
|---|---|---|
| Реляционные данные и кэш ответов бэкенда | `core:database` (Room KMP) | Правка сущности — новая версия `AppDatabase`; миграций нет: база хранит только копию данных бэкенда и при смене схемы пересоздаётся (`fallbackToDestructiveMigration`). Схема экспортируется в `schemas/`. Пока проект не выпущен; перед релизом это правило пересматривается. Устройство кэша — § Кэш |
| Настройки и маленькие значения | `core:datastore` (`DataStorePrefs`) | `core:datastore` — только хранилище ключ-значение без смысла полей. Что именно хранится (например, язык), описывает модель в `core:model`, маппинг и доступ — `core:data`; feature читает только через репозиторий |
| Скачанные файлы | `FileDownloader` (`core:data`), каталог из `CacheDirectoryProvider` (`core:cache`) | Только файлы; кэша данных в памяти и на диске рядом с Room нет |

- Размер, положение и «развёрнуто» окна Desktop хранит `WindowStateStore` в `desktopApp` (`java.util.prefs`): это
  состояние платформенного окна, а не пользовательская настройка, поэтому в `UserSettings` и DataStore его нет.
- Пути к файлам и базе дают платформенные провайдеры (`expect`/`actual`); в `commonMain` путей вида `/data/...`
  нет.
- Пользовательские настройки — `UserSettings` (`core:model`) через `UserSettingsRepository`; язык и другие поля
  читают оттуда, а не из DataStore напрямую.

## Кэш

Все данные бэкенда (фото, пользователи, коллекции, темы, статистика) сохраняются в Room типизированными таблицами;
база — единственный источник правды для экранов, бэкенд её обновляет. Так приложение открывается и листается без сети.
Других кэшей данных (в памяти, JSON-ответы, ключ-значение) нет: новый кэш — это таблица Room.

- Таблицы и DAO — `core:database`: `photo`, `user`, `collection`, `topic`, `statistics`, `total_stats`, `month_stats`
  и служебные `list_entry` / `list_state`. Сущность — `XxxEntity`, маппер `Xxx.toEntity(…)` и `XxxEntity.toDomain()` —
  в том же файле, что сущность (`core:database` зависит от `core:model`). Вложенные модели и списки лежат в колонке
  как JSON (`DatabaseConverters`).
- Порядок списка хранит `list_entry(listKey, position, itemId)`, а не таблица элементов: одно фото может быть в
  ленте, теме и коллекции одновременно. Возраст списка — `list_state(listKey, updatedAt)`. Ключи списков —
  `ListKeys` (`core:data`): вид списка и все параметры, ключ начинается с вида, чтобы сбрасывать целиком
  (`ListKeys.COLLECTIONS_PREFIX`).
- Постраничные списки: `CacheLoader.pager(…)` собирает `Pager` с `RemoteMediator` (`ListRemoteMediator`); экран читает
  `PagingSource` из Room (`list_entry` JOIN таблица элементов). Открытие: список моложе TTL показывается как есть,
  старый или ни разу не загруженный обновляется. Обновление (REFRESH) заменяет начало списка на месте и обрезает хвост,
  список на экране не пустеет; при сбое сохранённый список остаётся, а `LoadState.refresh` несёт `PagingLoadException`.
  Следующая страница считается по числу сохранённых элементов, поэтому работает и после перезапуска.
- Одиночные данные (фото, пользователь, коллекция, тема, статистика) и короткие списки (коллекции пользователя,
  связанные коллекции): `refreshableFlow(…)` / `refreshableListFlow(…)` в `core:data`, репозиторий отдаёт
  `Flow<Resource<T>>` (`getPhotoFlow`, `getUserFlow`, …). Экран читает только таблицу: сохранённая строка приходит
  сразу (`Resource.Success`), а если её нет — `Resource.Loading`. Параллельно запрос к бэкенду пишет ответ в таблицу
  через `CacheStore`, таблица эмитит новую строку. Каждая подписка обновляет данные заново, возраста и TTL у них нет;
  повтор после ошибки — новая подписка (`collect` ещё раз).
- Сбой бэкенда не трогает показанное: при сохранённой строке экран её оставляет (офлайн работает), без строки
  приходит `Resource.Error` с кодом. Сбой записи в базу не превращается в ошибку, если строка уже показана.
- Случайные фото (`getRandomPhoto`, `getRandomPhotos`): каждый вызов спрашивает бэкенд за новым набором и сохраняет
  его в `photo` и в список `photos:random:…`. Если бэкенд не ответил так, что подойдёт сохранённое
  (`canUseStaleData`: нет сети или ошибка разбора, 5xx, 403/429 как лимит запросов), показывается последний
  сохранённый набор для того же запроса. 401, 400 и 404 сохранённым не прячем.
- Действие `trackDownload` в базу не пишется: бэкенд требует сообщать о каждом скачивании, пропустить или
  подменить вызов нельзя.
- Сводка списка (то, что приходит в списках) не затирает подробности того же фото или пользователя (`CacheStore`):
  `exif`, теги, число скачиваний, e-mail, счётчики остаются, пока их не заменит полный запрос. Ссылки на картинки
  (`PhotoUrls`) остаются те, что сохранены первыми: каждый эндпоинт присылает свой `ixid`, и другая ссылка заставила бы
  загрузчик картинок скачать то же фото заново (картинка мигает, кеш диска не срабатывает).
- Изменение данных (создание, правка и удаление коллекции, добавление фото) пишет ответ бэкенда в таблицу и
  сбрасывает возраст затронутых постраничных списков (`CacheStore.invalidateLists`): они перезагрузятся при открытии,
  а сохранённое пока остаётся на экране. Открытые экраны обновляются сами, потому что читают ту же строку; принадлежность
  фото коллекциям пользователя (`currentUserCollectionIds`) правится в таблице `photo` (`changePhotoMembership`).
- `UserRepository.currentUser` — `StateFlow`, собранный из таблицы `user` (строка с `isCurrent`), поэтому приложение
  стартует с сохранённым пользователем, пока бэкенд не ответил.
- Очистка. Когда сессия закончилась (выход, 401 или токен убран другим способом), `SessionDataCleaner` стирает всё
  пользовательское: каждую таблицу (`CacheDatabaseCleaner`), скачанные файлы (`FileDownloader.clear()`) и
  вошедшего пользователя; кэши картинок чистит UI при показе экрана входа (`ClearImageCacheEffect`). Настройки
  приложения (тема, компоновка, язык) остаются. Room KMP не умеет `clearAllTables`, поэтому новая таблица
  обязательно добавляется в `CacheDatabaseCleaner.clearAll()`.
- Транзакций вокруг записи нет (в Room KMP нет общего `withTransaction`): записи устроены так, чтобы промежуточное
  состояние было безопасным — сначала элементы, потом порядок; начало списка заменяется на месте, а не удаляется.

## Загрузка файлов

`FileDownloader` (`core:data`): `getOrDownload(url, name)` возвращает путь к файлу в кэше и повторно не скачивает.

- Параллельные запросы одного файла ждут первую загрузку.
- Файл пишется во временный путь и переносится атомарно; пустой ответ — ошибка, а не файл.
- Расширение определяется по URL (`formatFromUrl`); имя файла — `name`, приведённое к безопасному виду.

## Пагинация

`androidx.paging` (мультиплатформенный): `paging-common` в `core:common`, `paging-compose` в `core:design-system`.

- Репозиторий данных бэкенда отдаёт `Flow<PagingData<T>>` через `CacheLoader.pager(…)` (Room + `RemoteMediator`,
  § Кэш). `createPager(pageSize) { page, loadSize -> Response<List<T>> }` из `core:common` — страничный список без
  базы, для данных, которые не кэшируем.
  Первая страница — 1; страница короче запрошенной — последняя. `initialLoadSize` равен `pageSize`, не меняем:
  иначе арифметика номеров страниц ломается.
- Ошибка страницы приходит как `PagingLoadException` с HTTP-кодом.
- В `Logic` поток кэшируется `cachedIn(coroutineScope)`, в Ui — `collectAsLazyPagingItems()` (`design/foundations.md`
  § Списки).
- Ошибка `RemoteMediator` тоже приходит как `PagingLoadException` с HTTP-кодом: экран показывает её, только если
  в списке ещё нет сохранённых элементов.
